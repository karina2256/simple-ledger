### 1.2 数据层（`src/main/db/`）

- **连接**：`journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON`、`busy_timeout=5000`，每次提交都 fsync。
- **完整性校验**：启动时 `PRAGMA quick_check` + `foreign_key_check`，不通过就弹窗给出数据目录和备份目录路径后退出。
- **迁移器**：`PRAGMA user_version` + 顺序迁移数组，`001_init` 建了 8 张表（accounts / categories / records / attachments / recurring / budgets / settings + 索引），字段与第一轮方案一致，`records` 多一个 `channel` 字段。
- **首次预设**：2 个账户（微信、支付宝）、15 个一级分类 + 二级子分类（餐饮/交通/购物/居住/娱乐/医疗/教育/人情/其他支出，工资/理财/副业/红包/退款/其他收入），靠 `settings.seeded` 标记防重复写入。
- **仓储层**：每张表一个 repo，纯 SQL；业务口径放在 service。
- **附件**：复制到 `<数据目录>/attachments/年/月/<uuid>.<ext>`，库里只存相对路径。

金额一律存「分」（`INTEGER`），时间戳存毫秒，业务日期存 `YYYY-MM-DD`。删除均为软删除（`deleted_at`），支撑「撤销删除」。

### 1.3 进程间通信

`src/shared/ipc.ts` 里集中定义通道名与 `Api` 契约，主进程注册、preload 暴露、渲染进程调用三边共用同一份类型。共 26 条通道，覆盖 app / settings / accounts / categories / records / attachments。

安全边界：`contextIsolation: true`、`nodeIntegration: false`、`webSecurity: true`；渲染进程拿不到任何 Node 能力，数据库只有主进程能碰。收据图片通过主进程注册的 `ledger://` 协议读取，路径越界直接 403。

## R1. 数据结构变更（迁移 002）

| 变更 | 说明 |
| --- | --- |
| `accounts.is_archived` / `accounts.archived_at` | 归档标记与归档时间 |
| `accounts` 表的 `name` 约束 | 原来的全局 `UNIQUE(name)` 换成部分唯一索引 `idx_accounts_name_live ... WHERE deleted_at IS NULL`，顺带修掉「软删除过的账户名永久占位」的老毛病 |
| `recurring.to_account_id` | 补上转入账户字段。001 里 `recurring.type` 允许 `transfer` 却没有对方账户，归档迁移时无法判断转账双方 |

迁移在 `foreign_keys = OFF` 下重建 `accounts` 表（PRAGMA 在事务里是空操作，所以由执行器在事务外开关），
迁移后自动跑一次 `foreign_key_check`，有异常直接抛错回滚。

**转账字段**：`records` 本来就有 `account_id` + `to_account_id` 两侧，不需要改 schema，因此没有破坏已有数据。
`budgets` 表只有分类维度、没有账户字段，所以「迁移预算」这件事在当前模型下不存在——见 README 说明。

## R2. 删除与归档规则

| 情况 | 行为 |
| --- | --- |
| 余额 0 且无记录 / 周期规则 | 真删除 |
| 其它 | 弹窗二选一：仅归档 / 迁移并归档 |

- 归档账户：不出现在新增 / 编辑下拉与默认筛选中；历史记录仍显示名字与金额；设置页「已归档账户」可查看、可恢复。
- 恢复：重新出现在下拉与筛选中，历史记录不变；若存在同名在用账户，恢复被拒绝并提示先改名。
- 迁移并归档（单事务）：记录两侧引用 + 周期规则两侧引用一并迁移；源账户初始余额并入目标账户初始余额；
  合并后变成「自己转自己」的转账软删除（可恢复、不影响余额）；变成自己转自己的周期规则自动停用；源账户随后归档。

## R3. 附件规则

- 软删除 / 撤销删除：只动 `deleted_at`，物理文件不碰。
- 彻底删除：记录行从库里移除（`attachments` 行随外键级联删除），弹窗询问是否同时删除收据文件，**默认不勾选**。

我推荐分类采用与账户**同一套**规则的理由：
- 两处行为不一致会让人记不住——「账户能归档、分类只能删不掉」很容易踩坑；
- 分类比账户更容易被塞满记录（一个「餐饮」可能挂着几百笔），硬禁止删除在实际使用中会变成死角；
- 归档不动历史记录，恢复也只是一下点击，代价比「删不掉」低得多。

## R7. 分类归档（迁移 003）

| 变更 | 说明 |
| --- | --- |
| `categories.is_archived` / `categories.archived_at` | 归档标记与时间，直接 ADD COLUMN，不需要重建表 |
| 归档范围 | 一级分类归档时，其子分类一并归档（`archivedChildren` 会回报连带数量） |
| 删除判定 | 没有记录（含子分类下的）且没有子分类 → 真删除；否则返回 `NEEDS_DECISION` |
| 迁移并归档 | 单事务：该分类（含子分类）下的记录改挂目标分类；预算一并迁移（目标已有同周期预算时保留目标那条）；整棵子树随后归档 |
| 迁移限制 | 只能同类型之间迁移（收入↔收入、支出↔支出）；目标不能是归档状态 |
| 恢复 | 子分类一起恢复；上级仍归档时先恢复上级；同级有同名在用分类时拒绝并提示改名 |
| 名字复用 | `nameExists` 改为只看未归档的分类，归档后名字可以重新使用 |
| 表单校验 | 记录新增 / 编辑时，归档分类会被拒绝（`该分类已归档，请重新选择`） |
| 界面 | 分类页删除按钮走同一套三选一弹窗；分类页底部新增「已归档分类」区，可查看与恢复 |

自测覆盖见 R4 里的分类用例（10 条），升级路径覆盖见 003 迁移（`categories` 两列 + 数据保留）。
